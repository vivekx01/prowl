How the pieces connect

companies → job_listings (1:many, deduped by company_id + job_req_id) → job_scores + applications (1:many per user, each capped at one row per user+listing via a unique constraint).

job_scores and applications are both scoped by user_id — the same listing can carry a different score and application status per user, since Prowl is multi-tenant (multiple users can each run their own resume against the same scraped listings).

scrape_runs/score_runs don't have FKs into the data they produce — they're just progress/telemetry rows per Celery task run, with their own *_run_logs child tables for streamed log lines (shown live in the UI while a run is in progress).

Lifecycle: one scrape → score → apply cycle

1. Celery Beat / manual trigger
→
2. new scrape_runs row (status=pending)
→
3. per-company scrape, insert/touch job_listings
→
4. run completes → if user has score_align_with_scraping setting, auto-queue a score run
5. new score_runs row (per user)
→
6. Stage 1 filter + Stage 2 score against profile.content
→
7. insert job_scores row per listing (score, verdict, reason)
→
8. high scorers → notify.py → Telegram
9. user reviews in UI, creates/updates an applications row (saved → applied → ...)

Key constraints & design notes

RuleWhereWhy
uq_company_job job_listings (company_id, job_req_id) Prevents re-inserting the same posting on every scrape; existing rows just get last_seen_at bumped.
uq_user_listing_score job_scores (user_id, listing_id) One score per user per listing — re-scoring overwrites rather than duplicates.
uq_user_listing_app applications (user_id, listing_id) One application-tracking row per user per listing.
uq_user_setting settings (user_id, key) Per-user key/value settings store (e.g. score_align_with_scraping), no fixed schema needed per setting.
no migration framework db/database.py: _migrate() Tables are created via create_all() on a fresh DB; existing deployments get hand-written ALTER TABLE statements run idempotently on every startup instead of Alembic-style versioned migrations.
retention runner.py: cleanup_old_listings Listings older than LISTING_RETENTION_DAYS are purged daily (2 AM IST via Celery Beat), unless tied to an applications row — so tracked jobs never silently disappear.
nullable user_id on scores/applications job_scores.user_id, applications.user_id Nullable for legacy/system rows, but in practice always set once multi-user auth is in place.
